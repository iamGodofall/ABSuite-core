# Deploying on Render

Two paths, and the difference between them is not cost. It is whether the
records survive.

---

## The one thing that decides everything

`docs/HOSTING.md` states the constraint and it is not negotiable:

> A chain has one head. Every execution record links to the one before it by
> hash… That is why storage is SQLite with a single writer, an `RWO` volume and
> a `Recreate` deployment strategy. **Any hosting decision that breaks that
> breaks the product.**

It also names the failure, about Cloud Run, in words that apply to any host with
no persistent disk:

> **Its filesystem is ephemeral.** A SQLite file written to local disk is gone —
> along with every record ever written. The chain would not even break; it would
> simply cease to exist, quietly, on a redeploy nobody thought was risky.

**Render's free instance types have no disk.** That is why `render.yaml`
specifies `plan: starter` and declares one: a disk is only attachable to a paid
instance. A free deploy of that blueprint is not a cheaper version of it. It is a
notary that forgets every signed record each time it restarts, while continuing
to answer `/health` with `"status":"healthy"`.

That failure mode is worse than being down. A customer's evidence disappearing
without an error is the exact thing this product exists to make impossible.

---

## Path A — the demo instance (free, and honest about it)

Use `render.free.yaml`. It removes the disk, keeps everything else, and sets
`ABSUITE_STORAGE_IS_EPHEMERAL=true`, which makes the server say at every boot
that records will not survive a restart. Nothing about it pretends otherwise.

**What it is good for**, and this is not a small list:

- A live URL for `@absuitecore/mcp`'s README, so a stranger can try a governed
  tool call without a sales call.
- Showing an auditor the verification flow end to end during a conversation.
- Exercising a Paystack, Stripe or PayPal webhook against a real public URL,
  which is the one thing that cannot be tested locally.

**What it must never be used for**: anybody's real records. Not a pilot, not a
"just for now", not a first customer while an upgrade is pending.

```
Render → New → Blueprint → point at this repo → render.free.yaml
```

Free web services also sleep after inactivity, so the first request after a
quiet period waits for a cold start. For a demo that is fine. For a webhook it
is not — a processor that times out will retry, but a sleeping instance makes
delivery unreliable in a way you will spend an afternoon misdiagnosing.

## Path B — the real instance (Render Starter + a 1 GB disk)

Use `render.yaml`, unchanged. This is the configuration the repository was
written for: one always-on service, one writer, one disk, `Recreate` on deploy.

At the time of writing that is Render's cheapest instance type that can hold a
disk. **Check the current price on Render's pricing page rather than trusting a
number written down here** — a figure in a document ages badly and this one has
no way to check itself.

### Before the first deploy

One value must be generated by hand and pasted in, and it is the one that
destroys data if you get it wrong later:

```bash
node scripts/gen-deploy-secrets.mjs
```

That prints `CAPKIT_TRACE_PRIVATE_KEY` and `CAPKIT_TRACE_KEY_ID`. They are
marked `sync: false` in the blueprint precisely so Render cannot generate them:
the key is Ed25519, it has structure, and **it must stay the same forever.** A
new one makes every record written under the old one fail verification. Set it
before the first record exists, not after.

Everything else (`CAPKIT_ADMIN_KEY`, `CAPKIT_HMAC_SECRET`,
`ABSUITE_ADMIN_API_KEY`, `ABSUITE_PUBLIC_PASSWORD`) is `generateValue: true` and
Render creates it, once, without printing it to a build log. Read them from the
dashboard's Environment tab.

### Also set, per what you are selling

| | |
|---|---|
| `ABSUITE_SIGNUP_ENABLED=true` | defaults to `false`; without it `/signup` is closed and nobody can create an account |
| `PAYSTACK_SECRET_KEY` | the `sk_…` key — signs webhooks AND authorises charges, so treat it as a payment credential, never an env file in git |
| `STRIPE_WEBHOOK_SECRET` | if selling through Stripe |
| `PAYPAL_WEBHOOK_ID` | if selling through PayPal |

### Then point the processor at it

| processor | webhook URL |
|---|---|
| Paystack | `https://<service>.onrender.com/billing/paystack/webhook` |
| Stripe | `https://<service>.onrender.com/billing/webhook` |
| PayPal | `https://<service>.onrender.com/billing/paypal/webhook` |

### Verify by content, not by the dashboard

A green deploy badge is a claim about a build, not about what is serving.

```bash
curl -s https://<service>.onrender.com/health
curl -s https://<service>.onrender.com/executions/public-key   # the auditor's anchor
```

Then **restart the service once** and re-verify the chain. That single step
proves the trace key survived, which is the only failure here that loses data
silently.

---

## Which one, and when

Path A costs nothing and makes the product demonstrable, which is what an
assessment conversation actually needs.

Path B costs money and is required the moment anyone else's records are in it.

There is no rush to Path B, and `docs/SERVICES.md` §1 says why better than this
file can:

> These need no new product. They need a phone call and a repository. For
> someone with no capital they are the only category that pays this month.

The audit and the deployment engagement run **on the customer's own
infrastructure**, on the customer's own disk. They carry no hosting cost at all.
The hosted notary is the second product, and the first customer is what should
pay for it.
